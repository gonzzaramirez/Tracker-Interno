# Taste
- Communicates in Spanish (rioplatense: "querés", "vos") and expects the product UI and copy to be in Spanish too. Confidence: 1.0
- Wants a UI that is "super intuitiva y fácil a la vista" — prioritizes intuitive navigation and visually clean, easy-to-scan interfaces. Confidence: 0.9
- Favors simple, practical tools that are quick to use over feature-heavy ones: e.g. easy copy-paste snippets for a knowledge base, a month-at-a-glance calendar to see who is unavailable, easy feedback entry. Reiterates "super simple" for new features (e.g. quick absence marking). Confidence: 0.95
- Expects the entire UI to be in Spanish, including third-party component defaults (e.g. date picker month/day names rendering in English) — when the user flags English text in the UI, they expect the agent to proactively review and fix the root cause across the app, not just the flagged spot. Confidence: 0.8
- Wants fast consecutive data entry: after saving a record (e.g. marking an absence), the form should auto-reset and stay open/ready for the next one so the user can log several entries in a row without re-opening or reloading. Confidence: 0.7
- Explicitly wants everything as visual as possible ("mientras más visual todo mejor"): prefers charts, heatmaps, kanban boards, sparklines and dense graphical views over text-based ones. Confidence: 0.9
- Open to adopting well-maintained community React components/libraries that fit the existing stack (Base UI + Tailwind v4 + Recharts) rather than building from scratch or migrating to heavyweight/licensed alternatives. Confidence: 0.6
- Considers the team calendar a fundamental feature of the product ("es algo fundamental") and cares most about its quality/usability. Confidence: 0.9
- Prefers the agent to propose a plan and build it directly in one go ("Propone el plan para las nuevas features y construi") rather than pausing for approval after presenting the plan — expects autonomous plan→implement→verify→summarize delivery. Confirms follow-up phases with terse one-word approvals ("Si") and expects the agent to continue implementing without further direction. Confidence: 0.9
- Works on a Windows environment: Unix-only shell tools (e.g. `head`) are unavailable, so the agent should use PowerShell equivalents (e.g. `Select-Object -First`) for inspecting output. Confidence: 0.8
- Does not work with git/version control — everything is local-only ("No estamos trabajando en repo, todo local"). The agent should not propose commits, branches, or repo hygiene; focus on the app being runnable on the machine. Confidence: 0.8
- Defines "listo" (done/ready) as the app actually running locally — verifies by building successfully and hitting the dev server pages (HTTP 200) rather than just making code changes. Confidence: 0.6
- Before a big rebuild, explicitly asks to be asked questions to iterate on scope ("haceme preguntas para iterar y construir todo de nuevo") and responds well to structured multiple-choice questions with "Recommended" options; after the discovery round, expects the agent to implement autonomously. Confidence: 0.8
- Product vision is a personal/single-owner tool: the platform exists so the owner tracks how their users improve and perform — tasks are purely informational (no assignment, no ownership, no statuses) and features that don't serve that core (kanban/priorities, snippets, check-ins, approval flows) should be removed rather than kept. Confidence: 0.8
- The core daily tracking is "asistencia" (presence — who said good morning and is active today), explicitly NOT "ausencias": the dashboard quick-mark records who is present, while time off (licencias/vacaciones) is a separate calendar concept. When the agent built the wrong concept, the user corrected it tersely and expected the whole flow to be rebuilt around presence (with obsolete code removed). Confidence: 0.85
- Expects core tracked records (attendance) to be fully manageable from the panel with a dedicated view: a complete CRUD (create, edit, delete) plus a log that shows the wall-clock time (HH:MM) each mark was made — a quick toggle that only stores the date is not enough ("necesito ese crud y la vista de eso en el panel"). Confidence: 0.85
- Wants all dates and times in the app pinned to Argentina time (America/Argentina/Buenos_Aires) for capture and display, regardless of where the server/DB runs (e.g. Turso/Vercel in UTC) — a central timezone helper must be used everywhere instead of server-local `new Date()`/`toISOString()`, fixing the whole app when a timezone bug is found, not just the flagged spot ("que siempre sea hora arg y todas las horas tambien de toda la app"). Confidence: 1.0
- Prefers day-list/history views to default to showing only today, with a date filter (date input + prev/next day navigation, capped at today) to browse previous days — rather than loading the full history by default ("que muestre solo la asistencia del dia y yo pueda filtrar y ver las anteriores"). Confidence: 0.9
- Wants the exact time of report to be captured AND displayed for every kind of logged record, not just the date — e.g. asked that tracking records save and show the hour ("que se guarde la hora y se vea despues en los seguimientos") so they can see when they logged a disconnection gap, and then extended the same "show creation time" treatment to tasks. The wall-clock time shown is Argentina time via the central date helpers. Confidence: 0.85
- When a storage format change is needed (e.g. tasks previously stored only a date and now need full timestamps), prefers the non-destructive option: new records store the new format while old records fall back gracefully (date only, no fabricated time), rather than running a data migration that backfills/rewrites existing rows. Confidence: 0.7
- Expects new feature work to follow the same design/behavior as existing similar features ("mismo diseño que seguimiento") — e.g. tasks should display creation time the same way tracking records do, reusing the shared date helpers rather than introducing a divergent pattern. Confidence: 0.6
- Wants the codebase to stay on current conventions for the installed framework version and expects the agent to remember it: the project is on Next.js 16.3, where the "middleware" file convention is deprecated in favor of "proxy" — deprecated patterns/warnings should be proactively migrated (rename file + function, keep logic identical) rather than ignored ("acordate de que estamos en nextjs 16.3... use 'proxy' instead"). Confidence: 0.9
